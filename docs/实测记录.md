# 实测记录 · Y9000P 2022 (82RF) 风扇 / 功耗 EC 接口

所有结论都是在本机 (NVEMIY, LENOVO 82RF, i7-12700H + RTX 3060, Windows 11 26200) 用
`tools\probe*.ps1` 逐个调用固件 WMI 接口跑出来的，原始输出留在 `logs\probe*.log`、`logs\smoke*.log`。
探测脚本本身是只读或"只往高提 + 自动收尾"的，不会把转速压到安全线以下。

## 1. 机型与接口位置

| 项 | 实测值 |
|---|---|
| `Win32_ComputerSystem.Model` | `82RF` |
| PnP 设备 | `LENOVO 82RF` / `FAM_LEGION_Y9000P_IAH7H` |
| CPU / GPU | i7-12700H (14C) / RTX 3060 Laptop |
| WMI 提供方 | `WmiProv` + `wmiacpi.sys`（ACPI-WMI，固件自带） |
| 设备路径 | `ACPI\PNP0C14\GMZN_0`（GameZone）、`ACPI\PNP0C14\WM00_0`（Lfc thermal） |

结论：**不需要装 Lenovo Vantage / Legion Toolkit**，接口在 BIOS 的 `_WDG` 里，Windows 通用 ACPI-WMI 驱动就能调。
但调用需要**管理员权限**（非管理员下 `Get-CimInstance` 直接 0x80041003 拒绝访问）。

## 2. 调用方式（踩过的坑，按这个写法才通）

| 写法 | 结果 |
|---|---|
| `Invoke-CimMethod -ClassName ... -Arguments @{FanID=1}` | ❌ 0x8004102F 无效的方法参数（一切方法都失败） |
| `ManagementClass` 类级 `InvokeMethod` | ❌ Invalid method Parameter(s) |
| `ManagementObject`（searcher 返回的实例）+ `GetMethodParameters` + `InvokeMethod(m, in, null)` | ✅ 可用（有入参的方法） |
| 同上，但对**无入参**方法调 `GetMethodParameters` | 返回 `$null` → 必须 `InvokeMethod(m, [ManagementBaseObject]$null, $null)` ✅ |
| `SELECT InstanceName FROM X` 拿到的对象 | ❌ 没有方法元数据，`GetMethodParameters` 返回 null —— 必须 `SELECT *` |

另外几个 PowerShell / 环境语言坑（都不是硬件问题，但都真实咬过我一次，记下来避免重犯）：

| 现象 | 根因 | 结论 |
|---|---|---|
| `R $FM 'Fan_...'` 报「找不到接受实际参数的位置形式参数」 | 别名优先级 **Alias > Function**，`R` 是内置 `Invoke-History`；同理 `Sv` = `Set-Variable` | 永远不要用 1–2 个字母命名函数 |
| `Sv 'smooth_samples' 5` 返回 `$null`，于是 `0 -gt $null` 为 **True** → 对空队列 `Dequeue()` 抛异常，守护进程第一轮就死 | 同上（别名抢走了函数），加上 PowerShell 的 `$null` 比较语义 | 数值读取函数改名 `Get-FanSafetyNum`，并 `TryParse` 兜底 + 循环条件加 `Count -gt 0` |
| 参数写成 `[hashtable]$Args` → 传哈希表时报「无法将 Object[] 转换为 Hashtable」 | 变量名**大小写不敏感**，`$Args` 就是自动变量 `$args`（未绑定参数数组） | 自动变量 `$args/$input/$matches/$host/$pid` 一律不做参数名 |
| 含中文的脚本运行时报「字符串缺少终止符」等一堆诡异语法错误 | Windows PowerShell 5.1 对**无 BOM** 文件按系统 ANSI（这台机器是 GBK）解码 | 所有 `.ps1/.psm1` 必须存成 **UTF-8 with BOM**（`tools/fix-encoding.ps1` 自动完成） |
| 面板 `/api/log` 永久卡死，导致之后所有请求超时；单独跑同一条命令也卡 | **`Get-Content -Tail N -Encoding UTF8` 在含中文的 UTF-8 日志上会挂死**（PowerShell 5.1 缺陷，与是否有其它进程写文件无关） | 一律用 `Get-SharedTailLines`（`FileStream` + `FileShare.ReadWrite` + 只读尾部字节）；日志追加用 `Add-SharedText`；面板改为读守护进程发布的 `state\logtail.json` 快照，请求路径完全不碰活动日志 |
| `/api/log` 返回 `{"value":[…],"Count":60}` 而不是数组 | 为了“防止数组被拆散”而写的 `return ,$lines` 造成二次包裹，`ConvertTo-Json` 于是按对象序列化它的属性 | 直接 `return [string[]]$lines`，调用方用 `@()` 包裹 |
| 工具脚本用 `python3` 静默不执行（改完文件内容没变） | `WindowsApps\python3.exe` 是微软商店占位 stub | 这台机器只有 `python` 是真的 3.11.1 |
| 守护进程改档位无效（`live.profile` 一直是旧值） | 在函数里 `$Profile = ...` 会创建**局部变量**，脚本作用域的原值不变 | 函数内写脚本级状态必须 `$script:Profile = ...` |
| 用 `Start-Process -Verb RunAs` 后终端像卡住 | 提升后的子进程继承了父 pipeline 的 stdout 句柄，父 shell 等句柄关闭 | 自动化里用 `-NoWait` + 轮询日志文件；面板/守护用 `-RedirectStandardOutput` 到文件 |

## 4. 控制模型（这台机器的真实行为）

1. **EC 接受手动转速并一直保持**，不会自己抢回去 —— 重新设置 Fn+Q 档位也**不会**释放手动控制权。
   彻底交还 BIOS 自动策略只有重启（实测：重启后回到 4500/4500 自动值）。
2. 风扇物理响应有 **~12s 斜坡**：命令后 +6s 大约在中间值，+12s 才稳定。所以控制周期不能按 2s 狂写。
3. 散热不足时 **EC 会自己动手砍功耗墙**（观测：PL1 115 → 45 W），同时伴随转速读数乱跳（0/800/1500）。
   这就是把 `SetFanSpeed` 当成 0–255 占空比误写（写 60 = 命令 60 RPM）后出现的现象。
   → 本工具把转速硬性夹在 2400–6600，并加了 8s 最小写间隔 + 迟滞 + 斜率限制。
4. BIOS 自动档怠速转速：安静 ≈3600 / 均衡 ≈4000 / 野兽 ≈4500；满速实测 6400–6600。

## 4b. 控制环时序（实测）

| 行为 | 时间 |
|---|---|
| 写入目标转速 → 转速读数中途到达 | ≈ 6 s |
| 写入目标转速 → 稳定到位 | ≈ 12 s |
| 满速开 → 6400 RPM | ≈ 4–6 s |
| 面板点击 → 守护消费 cmd.json | ≤ 2 s（一个循环周期） |
| Fn+Q 模式切换生效 | ≤ 1 s |

因此控制环参数定为：读 2 s 一次，写最多 8 s 一次，升速死区 200 RPM、降速死区 400 RPM、单次变化上限 900 RPM，
控制温度取 5 个样本（≈10 s）滑动平均 —— 都是围着上面那条 12 s 物理斜坡定的。

## 4c. 「写同一个值」也会重启斜坡（这条最反直觉，务必别用心跳重申）

观测于 2026-09-29 18:27–18:30，`logs/history.csv` / `state/live.json` 序列：守护进程按
`reassert_gap_s = 30` 周期性把**同一个** 5800 RPM 重新写进 EC，`logs/fan.log` 每 31 秒一条
`目标转速 -> 5800 RPM`，转速读数随之：

```
18:28:43  5800      ← 稳定
18:28:45  2600      ← 这条写入之后风扇直接掉到底
18:28:48  3900
18:28:50  5100
18:28:52  5800      ← 6~9 秒后才爬回来，然后一直等到下一次心跳
```

结论：**EC 的转速寄存器不是"设了就放着"，每次写入都会让风扇控制器重新从最低档开始爬**。
所以"怕 EC 被人改回去"而做定期重申，等于每 30 秒人为制造一次降速+再加速，噪音比不写更差。
现在只在 `|实际转速 − 目标| > 350 RPM` 且已过 `reassert_gap_s` 时才重申（这恰好覆盖了
"别人把 EC 改回去"的情形 —— 那时读数必然偏离）。

## 5. 故障复盘（为什么中途要你重启一次）

开发过程中我按"占空比 0–255"理解 `SetFan1Speed`，写了 60/255 这类值 → 等于命令风扇 60 RPM →
风扇接近停转 → EC 进入保护（PL1 砍到 45 W，转速读数错乱），且软件方式（满速开关、档位重设、写 255）都无法释放。
重启后 EC 重新初始化即恢复。**该风险已被 `Limit-FanRpm` 的区间夹取根除**（任何 <2400 的值都会被抬到下限，
写 0 也只会得到 2400），并新增 `test`/`reset`/`uninstall` 三条收尾路径都验证过能把机器带回正常值。

### 5b. 另两起"软件侧自己坑自己"（都转成了回归测试）

1. **曲线被整条拉平，风扇 64 °C 还跑 5800 RPM。** 面板曲线编辑测试把野兽档 8 个点的转速都存成同一个值
   （CPU 5800、GPU 4600），温度轴没动，所以曲线看起来"格式合法"。守护进程照曲线办事，于是一直高转速。
   查不清是谁改的 —— 因为**配置写入原来完全没有留痕**。现在：`Save-FanConfig` 记逐项 old→new 差异 +
   来源标签，`Get-FanCurveIssue` 把"恒定转速 ≠ 档位上限"判为可疑并在面板/日志/自检里报警，
   `state\config.prev.json` 永远留着上一版。
2. **出厂的「满速」档曲线本身是坏的。** `0:6600` 重复 8 次违反"温度必须递增"，`Parse-FanCurve` 直接抛，
   而守护进程把异常吞在每轮的 try/catch 里 —— 日志里刷了一排 `本轮异常: 曲线温度必须递增（0 重复或倒序）`，
   表现为"切到满速档反而不再调速度"。修了数据（`0:6600,20:6600,…,130:6600`），加了 `Repair-FanConfigCurves`
   自愈，并让"连续 3 轮异常"退回安全转速。**教训：任何"看起来只是配置"的东西都要被解析器验证一遍**，
   单测现在会遍历出厂配置的每条曲线跑一遍 `Parse-FanCurve`。
